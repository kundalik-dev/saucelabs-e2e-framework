# CLAUDE.md

## Project

JavaScript + Playwright Test E2E automation for **saucedemo.com**.

- Package manager: **pnpm** only (`pnpm ^11.18.0`)
- Node: **22.x LTS**
- Pattern: **Page Object Model (POM)**
- Test data: `test-data/` using `.json` / `.js`
- API testing: out of scope

## Commands

```bash
pnpm install
pnpm exec playwright install --with-deps chromium
pnpm exec playwright test
pnpm exec playwright test tests/ui/login.spec.js
pnpm exec playwright test -g "test name"
pnpm exec playwright test --grep @smoke
pnpm exec playwright test --list
pnpm exec playwright test --debug
pnpm run lint
pnpm run lint:fix
pnpm run format:check
pnpm run format
pnpm run report
```

Do not use `npm` or `yarn`.

## Architecture Rules

### Page Objects

- One class per page: `<page>.page.js` → `class PageName`
- Export the class as default.
- Constructor receives and stores Playwright `page`.
- Keep locators in the page object; tests must not call `page.locator()` directly.
- Prefer `getByRole()` / `getByTestId()`; CSS is acceptable when necessary.
- Locator properties use the `Loc` suffix: `usernameLoc`, `loginButtonLoc`.
- Page objects expose user actions/assertion helpers such as `login()`, `goto()`, `addProductToCart()`.

### Tests

- `tests/ui/`: validates one page in isolation.
- `tests/e2e/`: spans multiple page objects or represents a complete user journey.
- `tests/auth/`: auth setup specs (e.g. `login-setup.spec.js`) that write `storageState` to `auth/`.
- Use page objects and fixtures rather than raw selectors.
- Import test data instead of hardcoding reusable values.
- Use Playwright's retrying assertions for live UI state.

### Fixtures

- Located in `fixtures/`, named `<name>.fixture.js`.
- Extend Playwright `base` with `test.extend()`.
- Re-export `{ test, expect }`.
- `loginFixture` (`fixtures/login.fixture.js`) performs a real UI login; it does not use `storageState`.
- `tests/ui/cart.spec.js` instead uses `test.use({ storageState: "./auth/storageState.json" })`, generated by `tests/auth/login-setup.spec.js`. Both patterns currently coexist — check which a spec uses before assuming.

### Test Data

- Located in `test-data/`.
- JSON: `<page>.data.json` (e.g. `inventory-page.data.json`).
- JS: `<page>.data.js` when logic/structure is required (e.g. `users.data.js`, `login-page.data.js`, `inventory-sort.data.js`).
- Prefer data files over inline test literals.

### Utils

- Located in `utils/`, named `<name>.utils.js`.
- Use for pure, framework-agnostic helpers.
- Do not put Playwright/page/locator logic in utils.

## Naming

- Files: lowercase kebab-case — `login.page.js`, `common.utils.js`
- Variables/methods/properties: camelCase
- Classes: PascalCase
- Locators: camelCase + `Loc`
- Page objects: `<page>.page.js`
- Specs: `<feature>.spec.js`
- Fixtures: `<name>.fixture.js`
- Utils: `<name>.utils.js`

## Test Naming

Prefer:

```text
should <expected behavior> with <data>
should <expected behavior> when <action>
should <expected behavior> when <action> with <data>
should <expected behavior>
```

Examples:

```text
should login with valid credentials
should display error message when submitting empty form
should add product to cart when clicking on add to cart button
should display products list
```

## Playwright Config

`playwright.config.js` currently:

- Uses `https://www.saucedemo.com/` as default `baseURL`
- Uses `data-test` as `testIdAttribute`
- Loads `.env`
- Supports `BASE_URL`, `HEADLESS`, `RETRIES`, and `WORKERS`
- Defaults to headless mode
- Uses HTML reporter
- Uses `trace: "on-first-retry"`
- Enables **Chromium only**
- Firefox/WebKit/mobile projects are commented out
- Has **no** `snapshotDir`; visual testing is not configured

Do not enable additional browsers or introduce visual testing without checking the current project requirements.

## CI

`.github/workflows/playwright.yml` currently:

1. Runs lint + Prettier checks.
2. Runs tests after lint succeeds.
3. Installs Chromium only.
4. Runs headless.
5. Uploads the HTML report.
6. Uploads `test-results/` on failure.
7. Triggers on pushes to `main`; PR trigger is currently commented out.

Do not assume other workflows exist. Verify `.github/workflows/` first.

- `locked_out_user` — invalid/locked

- `wrong_username` — invalid username

## Important Gotchas

- Use `toEqual()` for already-resolved static arrays/values.
- Prefer `toSorted()` when sorting reusable arrays to avoid mutation.
- Import filenames exactly, including `.page`, `.utils`, and `.fixture` segments:
  `../utils/common.utils`, not `../utils/common`.
- Do not trust `docs/frameworks/` as proof that something is implemented; verify source/config/workflows.
- Visual baselines are OS-specific; generate them on the same OS as the test runner.
- Check `.vscode/playwright.code-snippets` for existing Playwright scaffolding snippets.

## Documentation

`docs/frameworks/01–07` are primarily reference/target-design documents.
`docs/frameworks/08–11` contain ratings, implementation notes, and historical/design information. Verify current code before treating them as authoritative.

`docs/test-cases/` contains the project's actual test-case documentation.

## Agent Rules

1. Inspect the existing implementation before creating or modifying files.
2. Follow the architecture and naming rules above.
3. Reuse existing page objects, fixtures, utilities, and test data.
4. Do not introduce unnecessary framework abstractions.
5. Keep tests readable and focused on behavior.
6. Run relevant tests/lint/format checks after changes.
7. When implementing a feature, update this file's **Current Structure** only if the project state actually changed.
8. Keep `CLAUDE.md`, `AGENTS.md`, and `copilot-instructions.md` synchronized when instruction changes are intentional.
